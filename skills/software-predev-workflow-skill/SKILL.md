# 软件前期研发工作流技能 V2.4

本文件是技能入口、阶段调度和通用规则。执行具体阶段时，必须读取下方映射中的参考文件；模板源文件位于 `templates/`。正式研发文档统一放在项目根目录 `docs/` 下。V2.4 根目录 `project.md`、`Task_Board.md` 和 `plans/done.md` 是项目管理记录例外。

## 1. 手动触发

可识别以下自然语言表达：初始化软件项目、启动软件前期研发流程、使用软件研发工作流、按软件前期研发规范初始化【项目名称】。触发后先判断是否已有项目名称和目标；缺少时只问最关键的一项，不重复询问已提供的信息。不得因普通讨论而擅自执行阶段转换。

## 2. 职责与不可违反原则

用户负责业务描述、澄清、产品/技术决策和交付物批准。助手负责原文保留、拆分编号、分类追踪、质量检查、提出问题与建议、维护项目文档。

1. 原始需求保留原文，不得以摘要替代。
2. 明确区分 `USER_ORIGINAL`、`USER_CLARIFICATION`、`ASSISTANT_SUGGESTION`、`USER_CONFIRMED_DECISION`。
3. 建议、假设、待验证结论不得自动成为正式需求或决策。
4. 需求、问题、决策、变更、风险、验收项使用稳定唯一编号；废弃编号不回收。
5. 不臆造业务规则、数值、技术能力、测试结果、审批人或审批时间。
6. 阶段评审与用户批准是两个独立动作；明确批准前不得标记 `APPROVED` 或 `BASELINED`。
7. 已批准基线不得静默覆盖；变更必须登记、影响分析、用户批准并保留历史。
8. 无法访问或写入持久文件时，明确说明只完成对话内整理，不能声称已保存到本地或资料库。
9. 发现项目文件间阶段、版本、编号不一致时先记录差异并报告，不擅自猜测修复。

## 3. 每轮执行协议

1. **恢复状态**：先读取项目状态、当前基线、需求/问题/决策/变更台账和最近批准文档。
2. **识别意图**：登记需求、澄清、分析、设计、评审、批准、变更、查询或结束工作。
3. **最小修改**：只修改请求涉及内容，保留来源、原文、编号和版本历史。
4. **同步追踪**：同步更新需求来源、关联问题/决策/变更和追踪矩阵。
5. **执行门禁**：提交评审或批准前运行对应检查表；有阻塞项时停止流转。
6. **反馈证据**：列出实际修改的文件、编号、阶段状态、未决事项和下一步。没有实际写入时必须说明。

## 4. 项目阶段

- `P0_PROJECT_INIT`：项目初始化与现状扫描。
- `P1_REQUIREMENT_COLLECTION`：原始需求采集、澄清、问题和决策登记。
- `P2_REQUIREMENT_ANALYSIS`：形成并评审 SRS。
- `P3_HIGH_LEVEL_DESIGN`：形成并评审概要设计。
- `P4_DETAILED_DESIGN`：形成并评审详细设计。
- 开发与测试属于后续工程阶段，文档分别归档至 `docs/05_Development/`、`docs/06_Testing/`；本技能可维护其前置追踪，但不将其伪装成已执行的开发或测试。

阶段推进必须满足对应参考规范和用户批准条件。用户可以要求跳过某阶段，但必须记录跳过理由、影响和风险，且不得伪造审批或基线。

## 5. 项目初始化

先区分新项目和已有项目：

- **新项目**：创建标准目录、项目章程、项目状态、文档清单和初始台账；按需复制模板到项目 `docs/templates/`。
- **已有项目**：先扫描目录、代码、文档、已有台账、当前基线和技术栈；输出现状、缺失项、冲突与风险。未经用户确认，不移动、覆盖、重命名或删除任何既有内容。

默认结构：

```text
<ProjectName>/
├── project.md                  # 项目摘要看板
├── Task_Board.md               # 统一任务台账
├── plans/
│   └── done.md                 # 已完成任务归档
├── docs/
│   ├── README.md
│   ├── templates/
│   ├── 00_Project_Management/
│   ├── 01_Requirements/
│   ├── 02_Architecture/
│   ├── 03_Detailed_Design/
│   ├── 04_Reviews/
│   ├── 05_Development/
│   └── 06_Testing/
├── src/
├── tests/
├── scripts/
├── config/
├── assets/        # 按需
├── tools/         # 按需
├── README.md
└── .gitignore
```

技术栈已有约定时优先遵循生态惯例。`assets/`、`tools/` 可按需创建。已有项目缺少目录时先报告；只有用户确认迁移/补齐范围后才执行。

初始化不得自动生成正式 SRS 或设计基线。用户已经提供的需求描述应作为首批原始需求登记。初始化完成不等于需求确认。

## 6. 编号与状态

- 原始需求 `RAW-001`；正式需求 `FR-001`、`NFR-001`、`BR-001`、`UIR-001`。
- 问题 `Q-001`；决策 `ADR-001`；变更 `CR-001`；风险 `RISK-001`；验收/测试 `AC-001`。
- 编号分配前扫描现有台账；发现重复/缺失先登记问题，不自行重编号。
- 风险台账使用 `RISK-001` 起的唯一编号，推荐实例路径为 `docs/00_Project_Management/Risk_Register.md`；风险状态、评估和应对记录以风险台账为准。
- 需求状态：`NEW`、`NEEDS_CLARIFICATION`、`PENDING_CONFIRMATION`、`CONFIRMED`、`MERGED`、`DEFERRED`、`REJECTED`、`SUPERSEDED`、`NEEDS_VALIDATION`。
- 阶段状态：`NOT_STARTED`、`IN_PROGRESS`、`REVIEW_PENDING`、`CHANGES_REQUIRED`、`APPROVED`、`BASELINED`。

## 7. P1 需求采集

自然语言输入默认进入需求采集。保留原始文本和可靠时间；识别新增、补充、修改、重复、冲突；拆分为可追踪条目；记录来源类型、分类、优先级、状态、关联问题与依赖；不确定项保持待确认。详细处理规则见 `references/03-requirements-management.md`。

用户明确要求当前只做需求采集时，必须停留在 P1：不得提前生成正式 SRS，不得进入概要设计。

## 8. P2 需求分析

只有用户明确启动且 P1 入口检查通过，才形成正式 SRS。SRS 必须包含项目范围/非目标、角色场景、业务流程与规则、功能/非功能需求、界面交互、数据配置、异常边界、外部约束、验收标准、风险假设、未决问题及 RAW 到正式需求的追踪矩阵。每项需求必须有编号、描述、优先级、来源、状态和可验证验收标准。不得编造未确认数值。

## 9. P3/P4 设计

P3 仅在 SRS 获用户明确批准后开始；覆盖系统上下文、架构选项与权衡、技术选型依据、模块职责与依赖、业务流程、数据模型、接口、安全性能可靠性兼容性、部署配置、风险验证及需求—模块追踪。

P4 仅在概要设计获用户明确批准后开始；按模块定义边界、组件职责、数据结构、接口输入输出/约束/错误、核心逻辑/状态机/时序、并发资源生命周期、异常日志、安全兼容、单元测试和需求追踪。

未经目标环境验证的技术结论标记 `NEEDS_VALIDATION`。

### 9.1 设计 Demo 生命周期（V2.3）

- Demo 采用**可交互网页原型**，作为设计讨论、评审和开发对齐参照；不替代 SRS、概要设计或详细设计文档，不新增研发阶段。
- P1/P2 不创建正式 Demo；可记录界面/交互设想并关联 RAW/Q。P3 在 SRS 获批准并进入概要设计后创建初版，验证整体布局、页面结构、视觉方向和核心流程。P4 在概要设计获批准后完善控件、状态、交互、异常反馈和页面联动。
- 正式项目 Demo 位于 `docs/design-demo/`，当前工作版本位于 `docs/design-demo/current/`；历史版本由 Git Commit/Tag 管理，不创建 `milestones/`、`history/` 等重复归档目录。Demo 不放入 `src/`。
- `docs/design-demo/README.md` 记录运行方式、目录和版本规则；`change-log.md` 记录重要变化、原因、影响、关联需求/CR/评审。按需复制技能包 `templates/` 中的 Demo 模板。
- P3 Demo 属于概要设计评审辅助物；P4 完成后，详细设计文档与 Demo 必须分别通过评审并获得用户明确批准，才可建立正式设计基线。两项批准范围、版本和关联关系均须记录；不得把一项批准推定为另一项批准。
- Demo 修改不得自动改变需求或设计基线。纯视觉/交互微调按草案修订记录；涉及需求语义、新功能、已确认行为或已批准设计的变化，按需求澄清/CR 流程处理。推荐不等于用户决定。
- Git 作为 Demo 里程碑版本管理前提：Commit 记录过程，Annotated Tag 记录重要里程碑；Tag 是仓库级并指向完整 Commit。普通里程碑可使用 `demo-v0.x`，正式基线使用 `demo-v1.0`，后续获批基线递增版本。正式基线 Tag 不得随意删除、移动或覆盖。Tag 必须指向稳定集成分支上的完整提交；无 Git 时先解决版本管理条件，不得声称已建立 Git 基线。
- 开发阶段以获批详细设计为规范依据，以正式 Demo 为视觉/交互参照。Demo 未展示的业务逻辑仍以设计文档为准；需要偏离正式基线时先走 CR，批准后更新相关文档/Demo 并按条件建立新 Tag。

## 10. 评审、批准与基线

标准流转：`IN_PROGRESS → REVIEW_PENDING → APPROVED → BASELINED`；退回时为 `CHANGES_REQUIRED`。评审提交包必须列出文档版本、检查结果、覆盖率、未决问题、风险和需用户决定事项。只有用户清晰表达批准，才能记录批准范围、版本、条件和可靠时间。部分批准不得把整份文档标为批准。建立基线时固定版本标识并保留可追溯历史。细则见 `references/05-review-and-baseline.md`。

## 11. 变更管理

任何已确认需求或已批准文档的修改都先建立 `CR`，说明原因、提出者、优先级、目标版本、原内容和建议；分析对需求、架构、模块、接口、数据、测试、风险和文档的影响；给出接受/拒绝/延期/待验证建议。未经用户批准不得写入正式基线。批准后更新追踪矩阵并识别需要重评的阶段。细则见 `references/06-change-management.md`。

## 12. 文档与持久化

正式文档使用 Markdown，存放在 `docs/` 对应阶段目录。文档头部至少包含名称/编号、项目、版本、状态、日期和修订记录。项目模板副本在 `docs/templates/`；技能包 `templates/` 只保存模板源文件。文件命名、文档头部、台账版本和基线标识必须一致。

网页环境若不能直接写入项目文件，提供完整可保存内容或可下载文件，并明确写入边界。不得声称已操作本地目录或资料库，除非实际写入成功。

## 13. 常用命令

识别但不限于：`初始化项目`、`查看项目状态`、`记录需求：...`、`澄清 RAW-xxx`、`查看需求台账`、`查看未决问题`、`查看决策记录`、`执行阶段检查`、`提交阶段评审`、`批准当前阶段`、`退回修改：...`、`新增变更：...`、`结束本次工作`。

## 14. 每轮响应

按实际情况说明：处理结果；新增/修改编号与文件；当前阶段/状态；待澄清项；阻塞与风险；下一步。简单事项简洁反馈，不重复整套规范。


## 15. 问题澄清全过程追踪（V2.2）

所有需要用户回答、选择或确认的问题，必须同时写入项目独立台账 `docs/00_Project_Management/问题澄清记录台账.md`，并与 `Q`、`RAW`、`ADR` 及阶段文档建立关联。该台账记录澄清过程，不替代原始需求台账、未决问题台账或决策台账。

每个澄清问题必须记录：问题编号及版本、问题原文、提出背景、影响范围/阶段、关联 RAW/Q/ADR、所有候选选项的完整描述、每项优点与缺点/代价/风险、助手本轮推荐选项及理由、推荐置信度（高/中/低）、依据与缺失信息、用户每次回答原文、后续讨论和选项修订、用户最终选择、确认表达/时间（可靠时）、当前确认状态。

**助手每次提出澄清问题或重新提交选项时必须给出推荐。** 推荐应基于已知信息；证据不足时仍给出当前最合理建议，同时标明低置信度、依据不足、未知条件及可能改变推荐的因素。推荐只是 `ASSISTANT_SUGGESTION`，绝不等于用户选择或批准。

历史采用追加式记录：不得覆盖用户首次回答、旧选项、旧推荐或此前选择。用户改选时新增一条记录并说明变化；用户未回答的选项不视为拒绝；部分回答不得标记整个问题已确认；用户暂缓需记录原因及重新触发条件；用户否决全部选项时保留否决原文并重新提出选项。

仅当用户明确确认具体选择/表述时，才可将该部分标记为 `USER_CONFIRMED_DECISION`，并同步决策台账。确认范围不清或只回答部分内容时保持 `PARTIALLY_CONFIRMED` / `PENDING_CONFIRMATION`。未经用户确认，推荐或候选方案不得写入正式需求、SRS、设计文档或基线。

该机制覆盖 P1 业务需求与功能行为、P2 需求边界/业务规则/异常处理/验收标准、P3 架构与技术方案/模块/数据方案、P4 接口/数据结构/算法/异常处理。跨会话必须恢复全部问题版本、选项、推荐、历次回答、讨论、改选和最终状态，不得只恢复最终结论。

## 16. 项目看板与任务管理（V2.4）

根目录 `project.md` 是只读摘要；根目录 `Task_Board.md` 是 TASK 字段、状态和历史唯一权威源；`docs/00_Project_Management/Project_Status.md` 是阶段状态唯一权威源；`plans/done.md` 是 DONE 任务追加归档。详见 `references/09-project-board-and-task-management.md`。

新项目按模板创建；已有项目先扫描，未经批准不得覆盖、迁移、重命名或删除。任务使用永不复用的 TASK 编号，具备明确执行目标和可验证完成条件；DONE 必须有证据并归档。任务类型使用统一枚举：`REQUIREMENTS`、`DESIGN`、`DEVELOPMENT`、`TESTING`、`DOCUMENTATION`、`REVIEW`、`PROJECT_MANAGEMENT`、`RISK_MITIGATION`、`RELEASE`、`OTHER`。项目确需扩展时使用 `CUSTOM:<名称>`，并在 `Task_Board.md` 的“项目扩展任务类型”表中登记定义后方可使用。任务完成不等于阶段完成、用户批准或基线建立。TASK 可关联 RAW/Q/ADR/CR/RISK/AC 及 Git Commit/Tag，但不替代专业台账或 Git 审批证据。风险由独立风险台账管理，推荐路径为 `docs/00_Project_Management/Risk_Register.md`。每轮实质工作结束时同步任务状态、证据、阻塞和唯一下一步；无法写入时标记待保存。

## 17. 项目一致性检查（V2.4）

按 `references/10-project-consistency-check.md` 在规定触发点**强制自动执行**只读检查，不得将其作为“按需”或可跳过步骤。触发点包括：新项目初始化完成后、已有项目扫描/接管交接后、TASK 新增后、TASK 任意字段修改后、TASK 状态变化后、TASK 关联关系变化后、DONE 任务从活跃区移入 `plans/done.md` 归档后、`Project_Status.md` 当前阶段发生变化后或阶段状态发生变化后（任一变化均独立触发检查）、阶段评审提交前、每轮实质工作结束前。一次操作同时命中多个触发点时，可合并为一次检查，但必须覆盖全部触发项。

结果为 `PASS`、`WARNING`、`FAIL`、`NOT_CHECKED`。检查不得自动修复文件、改变任务/阶段状态或操作 Tag；冲突只报告并等待用户决定。Git 或文件不可访问时如实标记 `NOT_CHECKED`，不得静默跳过或记为 `PASS`。每次触发均应在响应中说明检查范围和结果；无法执行时说明原因及未检查项。

## 18. 技能包升级报告归档（V2.4 维护规范）

技能包自身的版本升级、核对、复核和验收报告统一归档在根目录 `reports/`，按目标版本建立子目录，例如 `reports/V2.4/`。不得继续将版本报告散落在技能包根目录。

- 每个版本的报告只放入对应版本目录；文件名统一采用 `<版本号>_<报告类型>.md`。
- 报告类型按实际工作选择，包括 `升级方案`、`升级核对报告`、`复核报告`、`验收测试矩阵`；不要求每个版本必须生成全部类型。
- `reports/README.md` 维护归档规则和版本报告索引；每次新增或迁移报告时同步更新索引。
- 已归档报告作为历史审计证据保留。后续版本不得覆盖、删除或改写旧版本报告；需要补充时采用追加记录或新增修订报告，并明确修订关系。
- 根目录 `CHANGELOG.md` 继续维护跨版本变更摘要，不迁入 `reports/`。`audit-baselines/` 继续专门保存原始基线快照和对照证据，不与升级报告混放。
- 报告迁移或路径调整时，必须同步更新 `SKILL.md`、`README.md`、`reports/README.md` 及其他实际引用；不得改变报告正文的历史结论或测试状态。
- 该规则只管理技能包自身的升级报告，不改变用户项目文档统一放在项目 `docs/` 的约定，也不改变项目既有文件未经批准不得迁移的规则。
