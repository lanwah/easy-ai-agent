# 软件前期研发工作流技能包 V2.3

## 本版本

V2.3 在 V2.2 基础上增量增加可交互网页设计 Demo 生命周期、Git Commit/Annotated Tag 里程碑管理、Demo 双交付物评审与基线保护；不改变原有 P0-P4 阶段门禁、需求基线保护和用户审批原则。V2.2 的问题澄清全过程追踪规则及更早版本常用命令均予保留。

## 目录

- `SKILL.md`：技能入口、手动触发、阶段调度和通用规则。
- `references/`：8 份可执行详细规范，按阶段读取。
- `templates/`：项目初始化、状态、需求、问题、决策、变更、追踪、SRS、设计、评审及 Demo 管理模板源文件。
- `CHANGELOG.md`：版本变更记录。

技能包 `templates/` 是模板源目录；执行新项目初始化时，按需复制模板到项目的 `docs/templates/`。模板的中文源文件与英文逻辑名对应关系见 [templates/README.md](templates/README.md)。已有项目不会被自动覆盖模板。

**说明：** 项目初始化时不会把 `SKILL.md` 装进项目目录。日常在项目里做只读查询时，以本 README 的「常用命令」为准即可；完整阶段规则仍在技能包的 `SKILL.md` / `references/`。

## 常用命令

不要求逐字照抄；助手按意图识别。下列「只读」命令只汇总已有文档与台账，**不改文件、不推进门禁**。

### 只读查询（推荐日常使用）

| 说法示例 | 作用 | 主要依据文件 |
|---|---|---|
| `查看项目状态` | 汇总当前阶段、门禁状态、版本范围、阻塞项数量、待用户决定与下一步 | `docs/00_Project_Management/Project_Status.md` |
| `查看需求台账` | 列出原始/正式需求及状态、来源与追踪关系摘要 | `docs/01_Requirements/Raw_Requirements.md` 及 SRS / 追踪相关文档 |
| `查看未决问题` | 按阻塞 / 非阻塞 / 可延期排序列出未决问题 | `docs/01_Requirements/Open_Issues.md`（或问题台账） |
| `查看决策记录` | 列出决策、依据、状态与影响范围 | `docs/00_Project_Management/Decision_Log.md` |
| `查看变更记录` | 列出变更（CR）、影响分析与批准状态 | `docs/00_Project_Management/Change_Log.md` |
| `执行阶段检查` | 按当前阶段验收条件核对覆盖率与一致性；**只输出检查结果，不自动改状态** | 当前阶段文档 + 台账 + 检查表 |

每次进入项目，建议先发：`查看项目状态`。

### 写入与门禁（会改文档或推进阶段）

| 说法示例 | 作用 |
|---|---|
| `初始化项目：…` / `启动软件前期研发流程` | 新建或扫描接管；详见技能包 `SKILL.md` 第 4 节 |
| `记录需求：…` | 登记原始需求（P1 采集） |
| `提交阶段评审` | 生成评审包并进入 `REVIEW_PENDING`；**不自动批准** |
| `批准当前阶段` / `批准需求分析阶段` 等 | 仅当表达明确时执行审批 |
| `退回修改：…` | 记录评审意见并修订 |
| `新增变更：…` | 建立 CR 并做影响分析 |
| `结束本次工作` | 输出更新摘要、变更清单、待办与需保存内容 |

技能不会把「建议」「待验证」或「评审中」自动升级为已确认、已批准或已基线。推进门禁请用明确说法，例如「提交需求分析阶段评审」「批准需求分析阶段」。

## V2.3 增补：设计 Demo 与 Git 里程碑管理

V2.3 在 P3 概要设计阶段引入可交互网页 Demo，在 P4 详细设计阶段完善；P4 结束时，详细设计文档与 Demo 分别通过评审并获用户明确批准后，才能建立正式设计基线。Demo 不替代设计文档，不改变需求基线，也不新增研发阶段。

项目 Demo 路径为 `docs/design-demo/current/`，说明和运行约定放在 `docs/design-demo/README.md`，重要修改记录放在 `docs/design-demo/change-log.md`。不设置 `milestones/` 历史目录；Git Commit 记录日常过程，Annotated Tag 记录重要里程碑（例如 `demo-v0.1`、`demo-v0.2`、`demo-v1.0`）。正式基线 Tag 不得随意删除、移动或覆盖。具体规则见 `references/04-design-standards.md`、`05-review-and-baseline.md`、`06-change-management.md`。

Demo 只作为视觉和交互参照；业务规则、数据、接口和验收仍以获批设计文档为准。涉及需求语义或已批准设计变化必须经过需求澄清/CR，不得因修改 Demo 自动改变基线。

## 使用原则

1. 每次进入项目先执行“查看项目状态”，以项目文件中的最新记录为准。
2. 新项目按默认目录初始化；已有项目先扫描，未经确认不移动、覆盖、重命名或删除。
3. 所有项目研发文档统一放在项目根目录 `docs/`；项目实际使用的模板副本放在 `docs/templates/`。
4. 技能包自身的 `templates/` 是模板源目录，不是项目文档目录。
5. 按 `P0 → P1 → P2 → P3 → P4` 推进；评审、批准、建立基线是不同动作。
6. 用户明确要求停留在需求采集阶段时，不生成正式 SRS，不进入概要设计。
7. 未经用户批准不得修改已确认需求或已批准基线。
8. Demo 在 P3 引入、P4 完善；Git Commit 记录过程、Annotated Tag 记录重要里程碑；详细设计文档与 Demo 双重批准后才建立正式设计基线。

## V2.3 新增 Demo 相关命令建议

| 说法示例 | 作用 | 边界 |
|---|---|---|
| `查看 Demo 状态` | 汇总当前 Demo 路径、Commit/Tag、关联设计版本和评审状态 | 只读，不修改文件或 Git |
| `检查 Demo 与详细设计一致性` | 检查页面、交互、状态及追踪关系 | 只输出检查结果，不自动改基线 |
| `记录 Demo 修改：...` | 更新 Demo 变更记录并分析需求/设计影响 | 涉及基线的修改须先走 CR |
| `提交 Demo 评审` | 整理 Demo 评审包 | 不代表用户批准，不自动创建正式 Tag |
| `建立 Demo 正式基线` | 在条件满足且用户明确批准后建立基线记录与 Tag | 必须满足 Git、双重批准和稳定提交条件 |

## 网页版使用

为每个软件项目创建 ChatGPT Project，将 `SKILL.md` 加入项目指令，或上传本技能包并要求按其执行。手动输入：

`初始化项目：<项目名称>。请执行软件前期研发工作流。项目目标：...`

网页版是否能直接写入本地目录取决于当前连接与权限。不能写入时，助手必须提供可保存内容或下载文件，不能声称已经修改本地文件。


## V2.2 增补：问题澄清全过程追踪

V2.2 在 V2.1 全部目录、规则、模板和常用命令基础上增加独立问题澄清记录台账。原有 V2.1 常用命令与说明均予以保留。项目实例建议路径：`docs/00_Project_Management/问题澄清记录台账.md`。

新增只读查询命令（只读取并汇总记录，不修改文件、不推进门禁）：

| 说法示例 | 作用 | 主要依据文件 |
|---|---|---|
| `查看问题详情 Q-001` | 展示指定问题的原文、背景、选项版本、优缺点、推荐、用户回答和确认状态 | `docs/00_Project_Management/问题澄清记录台账.md` |
| `查看选项决策记录` | 汇总候选选项、每轮助手推荐、用户历次选择/改选和最终决策 | 澄清记录台账 + `Decision_Log.md` |
| `查看待确认选项` | 列出仍待用户选择、部分确认或暂缓的问题及触发条件 | 澄清记录台账 + `Open_Issues.md` |
| `查看阶段决策历史` | 按 P1/P2/P3/P4 汇总问题与选项决策沿革 | 澄清记录台账 + 阶段文档 |
| `检查问题记录完整性` | 检查选项、逐项优缺点、助手推荐及理由、用户回答/改选、最终确认和跨台账关联 | 澄清记录台账 + 质量检查表 |

**V2.2 强制规则：** 每次向用户提出澄清问题或重新提交选项时，助手必须给出推荐及理由，并标注置信度、依据和未知条件；证据不足时仍给出当前最佳建议但标注低置信度。推荐不等于用户决定。所有用户回答、选项调整和改选均追加保存，不覆盖历史；只有用户明确确认的内容才能进入正式需求/设计基线。
