# 10 项目一致性检查规范（V2.4）

## 1. 目的和边界

对 project.md、Task_Board.md、plans/done.md、Project_Status、专业台账和可访问 Git 信息执行自动只读检查。不得修改源文件、修复引用、改变任务/阶段状态或创建/移动/删除 Tag。

## 2. 触发时机和输入

以下触发点均为**强制触发**，不得按需选择或静默跳过：

1. 新项目初始化完成后。
2. 已有项目完成只读扫描并形成接管/交接结论后（即使尚未获准补齐文件，也要检查当前可见资料）。
3. TASK 新增后、TASK 任意字段修改后、TASK 状态变化后、TASK 关联关系变化后，以及 DONE 任务从活跃区移入 `plans/done.md` 归档后。
4. `Project_Status.md` 当前阶段发生变化后，或阶段状态发生变化后，任一变化均独立触发检查；同一轮两者同时变化时可合并一次检查，但报告必须注明覆盖两项。
5. 每次提交阶段评审前。
6. 每轮实质工作结束前。

同一轮操作同时触发多项时，允许合并执行一次，但报告必须注明覆盖了哪些触发点。第 6 项用于兜底，不替代第 1–5 项在关键操作后的即时检查。读取根目录看板/任务台账、完成归档、Project_Status、专业台账和文档清单。Git 仅在仓库可访问时检查；否则相关 Git 项标记 `NOT_CHECKED`。任何必要文件不可访问时也必须列出 `NOT_CHECKED`，不得省略检查或推定通过。

## 3. 检查项

- 看板恰有六节：项目目标、当前状态、关键决策、待办事项、风险、下一步；下一步恰一项；目标不超过三句，状态事实不超过五条。
- TASK 编号唯一、格式正确、必填字段齐全、任务类型属于 `references/09-project-board-and-task-management.md` §3 定义的统一基础枚举，或属于已登记的 `CUSTOM:<名称>` 扩展类型；TASK 状态合法、状态转换有效；BLOCKED 有原因，DONE 有证据；终态不得非法重开。
- 每个 DONE 均有 plans/done.md 归档，且不留在活跃区；CANCELLED/DEFERRED 不误记为 DONE。
- Project_Status 是阶段状态唯一权威源；看板阶段一致；评审、批准、基线有对应证据；不以所有任务 DONE 自动批准阶段。
- TASK 对 RAW/Q/ADR/CR/RISK/AC 引用有效；RISK 引用必须能在风险台账中定位，风险台账记录应具备唯一编号、风险描述、概率/影响评估、应对措施、责任人或待分配标记、合法状态（`OPEN`、`MITIGATING`、`ACCEPTED`、`OCCURRED`、`CLOSED`）及关联信息；`ACCEPTED` 必须有用户明确接受证据，`OCCURRED` 必须关联后续处置记录；TASK DONE 不自动关闭 CR。
- Git 可访问时验证 Commit/Tag 是否存在、引用可解析；Tag 不证明用户批准。Demo 正式 Tag 还须满足 V2.3 评审/双重批准/稳定提交门禁。

## 4. 结果分级

`PASS`：已检查且符合；`WARNING`：风险/信息不完整需人工确认；`FAIL`：明确规则违反、权威冲突、重复编号、DONE 无证据/归档；`NOT_CHECKED`：资料缺失或环境不可访问。不得用 PASS 掩盖 FAIL，不得把 NOT_CHECKED 统计为 PASS。

## 5. 报告和异常

每次强制触发均使用 `项目一致性检查报告模板.md` 或在本轮交付中按其字段完整报告，记录项目、日期、触发原因、范围、读取文件、各级数量、证据路径、问题、影响、建议和未检查项。未执行/无法访问的项目必须标记 `NOT_CHECKED` 并说明原因。冲突列出差异并等待用户决定；不自动修复、重编号、归档、改状态或改 Tag。
