# 06 变更管理规范

## 1. 适用范围

适用于已确认需求、已批准/已基线文档、架构决策、接口、数据结构、验收标准和项目范围的变化。未确认草案的普通修订也应保留版本记录，但不一定需要正式基线 CR；由项目规则决定。

## 2. 变更流程

1. 建立 `CR` 编号，不覆盖原内容。
2. 记录提出者、日期（可靠时）、原因、描述、优先级、目标版本和期望时间。
3. 描述当前基线与拟议差异，标注新增/修改/删除。
4. 影响分析：RAW/FR/NFR/BR/UIR、范围、架构、模块、接口、数据、性能/安全、部署、测试/验收、文档、进度/成本/风险。
5. 给出接受、拒绝、延期或待验证建议及依据。
6. 等待用户明确批准/拒绝；未经批准不修改正式基线。
7. 批准后更新受影响文档、台账、追踪矩阵和版本记录；标记需要重新评审的阶段。
8. 关闭 CR 前核实所有影响项已处理或明确延期。

## 3. 变更状态

建议使用 `PROPOSED`、`ANALYSIS_IN_PROGRESS`、`PENDING_APPROVAL`、`APPROVED`、`REJECTED`、`DEFERRED`、`IMPLEMENTED`、`VERIFIED`、`CLOSED`。状态转换必须有记录，不得将建议自动视为批准。

## 4. 基线保护

保留原始文本、原版本、批准记录和变更历史。新版本应能追溯到 CR；未受影响内容不得无理由重写。变更若改变用户需求含义，必须明确展示前后差异并取得确认。

## 5. 紧急变更

紧急不等于免审批。可先记录风险和临时措施，但需尽快补充正式影响分析和用户批准；不得伪造事后批准。


## 6. Demo 修改与版本变更（V2.3）

### 6.1 修改分类与处理

对 Demo 的每次有意义修改先分类：

1. 纯视觉调整（颜色、字体、间距、图标等）：记录变更原因和前后效果；确认未改变已批准的交互/需求语义后，可按普通设计修订处理。
2. 交互调整（控件行为、导航、反馈、状态变化）：检查是否改变已确认需求、验收标准或已批准设计；影响已批准内容时建立 CR。
3. 同一需求的实现方式调整：分析可用性、可访问性、兼容性、测试和详细设计影响；是否需要 CR 依据是否改变已批准设计基线判断。
4. 新增功能或需求语义变化：建立澄清记录并关联 RAW/Q/ADR；如影响已确认需求或已批准基线，必须建立 CR。不得仅通过修改 Demo 将其纳入范围。
5. 与已确认需求或批准设计冲突：暂停相关基线修改，记录冲突，向用户澄清；未经批准不得以 Demo 覆盖需求或设计文档。

### 6.2 Git Commit/Tag 规则

- 日常 Demo 修改以 Git Commit 留痕，提交说明应能识别修改目的和关联事项。
- 仅在重要设计节点、重要评审版本或正式基线创建 Annotated Tag；不要求每个 Commit 创建 Tag。
- Tag 是仓库级，必须指向包含完整 Demo 状态的 Commit；正式 Tag 在稳定集成分支创建。
- 正式基线 Tag 不得删除、移动、覆盖或复用。任何需要改变正式基线内容的行为均先建立并批准 CR，再创建新的正式 Tag。
- 历史版本通过 Git Tag/Commit 查看和比较，不另建 `milestones/`/`history/` 目录，也不通过复制文件夹维护重复快照。

### 6.3 开发阶段发现偏差

开发人员发现代码与正式 Demo/详细设计不一致时，先判断是实现偏差还是设计问题。实现偏差应修正代码；确需改变已批准设计时提交 CR，说明原因、差异、影响和替代方案。用户批准后同步更新详细设计、Demo、追踪矩阵和变更记录；达到正式基线更新条件时创建新 Annotated Tag。Demo 与详细设计冲突时以澄清/CR 结果为准，不得由开发人员自行选择。

## 7. V2.4 CR 与 TASK 关联规则

CR 仍是已确认需求、已批准设计和正式基线变更的权威记录；TASK 仅承载 CR 的分析、修订、验证等执行工作。一个 CR 可关联多个 TASK。CR 的 `APPROVED`、`IMPLEMENTED`、`VERIFIED`、`CLOSED` 与 TASK `DONE` 独立维护；TASK 完成不得自动关闭 CR。CR 关闭前仍须核对影响项、文档、追踪矩阵、评审和重新基线要求。
