# 03 需求管理规范

## 1. 需求信息分类

每条记录至少区分：原始表达、规范化摘要、来源类型、提出时间（可靠时）、分类、优先级、状态、关联问题/决策/变更、拆分或合并关系。来源类型只能使用：`USER_ORIGINAL`、`USER_CLARIFICATION`、`ASSISTANT_SUGGESTION`、`USER_CONFIRMED_DECISION`。

## 2. P1 需求采集

每次接收新信息：
1. 原样保存用户表达；不要只保存助手改写。
2. 判断是新增、补充、澄清、修改、重复还是冲突。
3. 拆分为单一、可追踪、可澄清的需求条目；每个拆分项保留原始来源关联。
4. 分配 `RAW` 编号；已有编号则继续使用，不重复新建。
5. 标注功能、非功能、业务规则、界面交互、约束或待分类。
6. 优先级可用 Must/Should/Could/Won't 或项目既有体系；未知则待确认，不替用户定优先级。
7. 记录需求状态和关联的 `Q`、`ADR`、`CR`。
8. 给出本次登记结果与少量关键澄清问题。

## 3. 需求状态

- `NEW`：已登记，尚未澄清。
- `NEEDS_CLARIFICATION`：存在歧义或信息缺失。
- `PENDING_CONFIRMATION`：已形成候选表述，等待用户确认。
- `CONFIRMED`：用户明确确认。
- `MERGED`：已并入其他条目，保留原编号及指向。
- `DEFERRED`：延期处理，记录理由/目标版本。
- `REJECTED`：用户明确拒绝或决定不纳入，保留原因。
- `SUPERSEDED`：被新条目替代，保留替代关系。
- `NEEDS_VALIDATION`：需要原型、试验或外部验证。

不能把登记完成等同于需求确认。助手提出的需求候选必须保持建议/待确认状态。

## 4. 澄清与冲突处理

- 一次只问最影响范围或设计的关键问题；允许用户部分回答。
- 对冲突需求分别保留原文，建立问题记录，描述冲突点、影响范围和可选处理方案。
- 不自行选择冲突项的最终答案；用户确认后更新状态并保留决策记录。
- 低风险未知可作为假设，但须标注责任人、影响和验证时机。

## 5. P1 完成入口检查

进入 P2 前核对：当前范围内已知原始需求均已登记；每条均有处理状态；关键歧义/冲突已澄清或登记为阻塞/待验证；范围和非目标已说明；问题已分级；用户明确要求启动需求分析。任一关键条件不满足则停留 P1。

## 6. P2 SRS 形成

SRS 应覆盖：目的、背景、范围/非目标、用户角色和场景、业务流程/规则、功能需求、非功能需求、界面交互、数据配置、异常边界恢复、外部依赖约束、验收标准、风险假设、未决问题和需求追踪矩阵。

每条正式需求使用 `FR`、`NFR`、`BR` 或 `UIR` 编号，至少包含名称、明确描述、优先级、来源 RAW、状态和可验证验收标准。验收标准应可观察、可测试；不得捏造用户未确认的数值阈值。

## 7. 追踪要求

维护 RAW → 正式需求 → 概要设计模块 → 详细设计章节 → 测试/验收项的双向追踪。合并、拆分、延期、拒绝和替代都要保留来源与去向。没有下游项时标记待设计/待测试，不留空造成误读。

## 8. 需求变更

已确认需求修改须创建 `CR`，记录原内容、新提议、原因、提出者、影响分析和用户审批状态。批准前只保留为提案，不覆盖原需求基线。

## 9. 澄清问题与选项的全过程记录（V2.2）

P1/P2 中每个需要用户回答或选择的问题，必须在项目独立文件 `docs/00_Project_Management/问题澄清记录台账.md` 建立记录，并关联 RAW/Q/ADR。未形成正式需求前，候选表述仍为待确认。

每次提问必须提供可理解的候选选项；每个选项写明完整含义、优点、缺点、代价/风险及适用条件。**助手每次必须给出推荐选项和推荐理由**，并标注置信度（高/中/低）、依据、未知信息及可能改变推荐的条件。即使证据不足，也应给出当前最佳建议并明确低置信度，不得把建议包装成事实。

完整保存问题原文、背景、影响范围、所有选项、推荐及理由、用户每次回答原文、补充讨论、选项变更、用户改选和最终确认。历史只追加不覆盖；选项变更保留旧版本。用户未选择的选项不代表拒绝；部分回答保持部分确认；暂缓记录原因和触发条件；全部否决则保留否决并重新提出方案。用户明确确认后才同步为决策记录。

澄清台账是过程记录，未决问题台账维护当前问题状态，决策台账维护正式选择，原始需求台账维护用户需求原文，四者通过编号互相引用，不得互相替代。
