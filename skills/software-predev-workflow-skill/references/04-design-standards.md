# 04 设计规范

## 1. 设计阶段入口

- P3 概要设计：对应 SRS 已由用户明确批准并建立可识别版本；若 SRS 未批准，不得开始正式概要设计。
- P4 详细设计：概要设计已由用户明确批准；按模块推进，不得跳过未解决的关键架构约束。
- 允许进行探索性讨论，但必须标记为草案/建议，不能称为正式阶段交付物。

## 2. 概要设计内容

至少包括：设计目标与原则；系统上下文；架构视图和候选方案；技术选型及依据；模块职责、边界和依赖；关键业务流程；核心数据模型；外部接口/集成；安全、性能、可靠性、兼容性；部署、启动、升级和配置；技术风险与验证计划；需求—模块追踪矩阵。

对关键方案说明候选项、优缺点、约束、成本/风险和选择理由。未经验证的技术结论标记 `NEEDS_VALIDATION`，列出验证方式和成功标准。

## 3. 详细设计内容

按模块记录：目标、职责、边界、组件/类职责、数据结构和持久化、接口输入输出/约束/错误、核心算法和流程、状态机/时序、并发和资源生命周期、异常处理/日志/诊断、安全权限/兼容、单元测试和验收标准、需求与概要设计追踪。

接口定义应明确类型、必选性、约束、错误行为和兼容策略。涉及数据持久化时说明结构、迁移、备份恢复和数据完整性（适用时）。

## 4. 设计质量

检查可实现性、可测试性、可维护性、模块内聚/耦合、故障隔离、可观测性、安全边界和运行环境约束。不要无意义地提前规定每个函数；设计深度以开发人员能一致实现、测试人员能验证为准。

## 5. 设计追踪与变更

每个模块/接口/数据实体应关联来源需求。设计变更若影响已批准需求或设计基线，必须走 CR；保留旧版本，更新追踪矩阵，并判断是否需要重新评审 SRS、概要设计或详细设计。

## 6. 设计阶段澄清与方案决策记录（V2.2）

P3/P4 对架构选型、技术方案、模块边界、数据方案、接口、数据结构、算法和异常处理等需要用户确认的事项，沿用独立问题澄清记录台账。每次向用户提出选择时，完整列出候选项、各自优缺点/代价/风险，并由助手给出推荐及理由、置信度和依据缺口。

保存每轮问题、选项版本、推荐、用户回答原文、讨论、改选和最终确认的追加式历史。用户确认前，任何候选设计都只能标为草案/建议，不得写入正式设计基线。用户明确确认的方案再同步到决策台账，并关联需求及设计版本。


## 7. 设计 Demo 生命周期与目录（V2.3）

### 7.1 定位与阶段

设计 Demo 采用可交互网页原型，用于让用户在编码前预览界面效果、讨论设计并为后续实现提供视觉/交互参照。Demo 是独立设计交付物，不替代 SRS、概要设计、详细设计、接口/数据规范或验收标准，不新增研发阶段，也不自动形成需求或设计决策。

- P1/P2：不创建正式 Demo。可将界面想法、参考样式和交互设想登记为原始需求、澄清问题或建议。
- P3：仅在 SRS 已获用户批准并进入概要设计后创建初版 Demo，覆盖整体布局、页面结构、主要视觉方向、导航和核心交互流程。初版用于探索和概要设计评审，不作为正式开发基线。
- P4：仅在概要设计已获用户批准后完善 Demo，覆盖具体页面/控件、状态、交互反馈、弹窗/菜单、正常/异常流程、空/加载/错误状态和页面联动。
- P4 结束：详细设计文档与 Demo 分别完成检查、分别提交评审、分别获得用户明确批准后，才可建立正式设计基线。任一项未批准，整体正式设计基线不得宣称完成。

### 7.2 目录与文件职责

项目 Demo 统一放在 `docs/design-demo/`，建议结构：

```text
 docs/design-demo/
 ├── README.md
 ├── current/
 │   ├── index.html
 │   ├── assets/
 │   ├── styles/
 │   ├── scripts/
 │   └── ...
 └── change-log.md
```

`current/` 是当前工作版本；`README.md` 说明用途、启动/运行方式、技术依赖、浏览器要求、目录约定和 Git 管理方式；`change-log.md` 记录重要修改、原因、影响、关联需求/问题/决策/CR/评审。Demo 属于设计资料，留在 `docs/`，不得混入 `src/`。不创建 `milestones/`、`history/` 等重复历史快照目录。

### 7.3 Git 版本管理

Git 是 Demo 里程碑管理的标准方式：

- Git Commit 记录日常修改及其原因；不要求每次 Commit 都创建 Tag。
- 重要设计评审、重大方向调整和正式基线使用 Annotated Tag。
- 命名建议：`demo-v0.1`（P3 初版）、`demo-v0.2`（概要设计评审版本）、`demo-v0.3`（重大调整）、`demo-v0.4`（P4 完善版本）、`demo-v1.0`（正式批准基线）；正式基线后按获批变更递增，如 `demo-v1.1`。
- Tag 是仓库级引用，指向整个 Commit，不是目录级标签。创建前必须确保该 Commit 包含完整、可运行/可检查的 Demo 快照；Tag 应建立在稳定集成分支的已提交状态上。
- 普通里程碑 Tag 也不得复用已发布名称；正式基线 Tag 受保护，不得随意删除、移动或覆盖。修改正式基线须走 CR，获批后创建新版本 Tag。
- Git 不可用时，不能宣称已完成符合本规范的 Git 里程碑管理；应先初始化 Git 并建立基本提交管理。不得默默改用重复目录快照替代本规范。

常用命令示例：

```bash
git tag -a demo-v1.0 -m "FolderHub Demo baseline

Stage: P4 Detailed Design
Demo-Version: 1.0
Design-Baseline: DD-BL-1.0
Review-Status: APPROVED
Approval: USER_APPROVED"
git tag -l "demo-*"
git show demo-v1.0
git diff demo-v0.2 demo-v1.0 -- docs/design-demo/
git checkout demo-v0.2
```

检出历史 Tag 仅用于查看/复核；继续开发前应切回正常分支，不直接在 detached HEAD 上工作。

### 7.4 Demo 与正式设计文档的关系

详细设计文档是业务规则、数据结构、接口契约、状态逻辑、安全约束和验收标准的权威依据；Demo 是界面视觉和交互行为参照。Demo 未展示的后台逻辑不代表无需实现；Demo 与文档冲突时不得自行选边，先记录差异并澄清。

### 7.5 设计 Demo 修改分类

- 视觉微调：颜色、间距、字体等；记录修改并检查可访问性/一致性。
- 交互调整：控件反馈、菜单展开、导航方式等；检查是否改变已确认行为。
- 实现方式调整：同一需求的不同 UI 实现；分析对设计、可用性和验收的影响。
- 新增功能/需求语义变化：建立需求澄清记录，必要时提交 CR；未经用户确认不得纳入正式需求。
- 与已确认需求/批准设计冲突：暂停相关基线修改，先澄清并按 CR 审批。

每项重要修改应记录修改前后、原因、关联需求/问题/决策、影响、处理方式、评审结果和对应 Commit/Tag。助手推荐不构成用户批准。
