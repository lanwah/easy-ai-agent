# 08 跨会话连续性规范

## 1. 会话开始

每次新会话或恢复项目时，优先读取：
- `docs/00_Project_Management/Project_Status.md`
- 原始需求、问题、决策、变更台账
- 当前 SRS/概要设计/详细设计及其批准/基线记录
- 文档清单、最近评审记录和未关闭 CR

以文件中的最新正式记录为准，聊天记忆只能辅助定位，不得覆盖文件记录。

## 2. 状态冲突

若不同文件阶段、版本、编号或状态不一致：记录冲突点、涉及文件、可能影响；标记为待核实；向用户报告。不得擅自选取一个版本作为真相或自动修复基线。

## 3. 会话结束

结束本轮工作时更新或提供更新内容：当前阶段/状态、当前需求/设计基线版本、已完成事项、文件修改清单、未决问题、阻塞/风险、决策、变更、下一步和需用户批准事项。没有实际写入时，明确标注“待保存”。

## 4. 最小交接摘要

交接摘要应短而可操作，至少含：项目名、当前阶段、当前基线、最后处理编号、待办/阻塞、最近变更、下一步。不要只写“继续上次工作”。

## 5. 资料缺失

缺少台账或基线文件时先说明缺失；可根据可见历史提出恢复候选，但标记为待用户确认，不得伪称恢复了权威记录。

## 6. 问题澄清历史恢复（V2.2）

恢复项目时，除原有台账外，必须读取 `docs/00_Project_Management/问题澄清记录台账.md`。对每个未关闭或影响当前基线的问题，恢复问题原文、背景、完整选项及版本、每项优缺点、每轮助手推荐及理由/置信度/依据、用户历次回答、补充讨论、改选过程、最终选择和确认状态。

不得仅保留最终结论而丢弃讨论历史；不得把助手推荐恢复成用户决定。若澄清台账缺失或与决策台账冲突，标记待核实并报告，不得猜测补齐。


## 7. Demo 状态与 Git 版本恢复（V2.3）

当项目已进入 P3/P4 或已有 Demo 时，恢复会话必须检查并记录：

- Demo 路径（通常为 `docs/design-demo/current/`）及运行说明。
- 当前 Git 分支、最新相关 Commit 哈希、工作区是否有未提交修改（若当前环境可访问 Git）。
- 已创建的 `demo-v*` Tag、各 Tag 对应阶段/用途，以及哪个 Tag 是正式基线。
- Demo 版本与 SRS/概要设计/详细设计版本、评审记录、正式设计基线的关联。
- `change-log.md` 中最近修改、未完成事项、已知限制和待解决差异。
- Demo 评审状态、用户批准范围/表达、未决问题和相关 CR。

历史 Tag 仅用于恢复查看/比较；继续修改应切回正常分支。不得仅凭 Tag 名称推断已获批准；必须核对评审与用户批准记录。若 Git 状态、Tag、文档版本或批准记录不一致，标记待核实并报告，不自动移动/删除 Tag、不猜测正式基线。

如果当前会话无法访问仓库或执行 Git 命令，应向用户索取最新 `git status`、`git log`、`git tag -n` 等输出或相关记录，并明确状态尚未验证；不得声称已经检查仓库状态。

## 8. V2.4 看板与任务连续性恢复

恢复项目时读取根目录 `project.md`、`Task_Board.md`、`plans/done.md`（若存在），以及原有 Project_Status 和专业台账。阶段以 Project_Status 为准，任务以 Task_Board 为准，完成归档以 done.md 核对；project.md 仅作摘要。发现冲突先报告，不自动修复。恢复最后处理 TASK、阻塞、依赖、完成证据、RAW/Q/ADR/CR/RISK/AC 和 Git Commit/Tag（若可验证）。会话结束时判断本轮是否产生需跨会话跟踪的任务，追加状态历史和完成证据；不得把每条对话机械创建为任务。
