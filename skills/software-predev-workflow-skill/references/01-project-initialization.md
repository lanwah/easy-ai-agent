# 01 项目初始化规范

## 1. 目标与原则

初始化的目标是建立可持续维护的项目骨架、状态记录和台账，不是替用户补写未经确认的需求或设计。初始化分为新项目和已有项目两条路径。项目名称、目标、平台、版本范围等未知信息必须标为待确认。

## 2. 输入

- 项目名称和目标（至少需要项目名称；缺目标时询问一项关键问题）。
- 项目类型：新建或已有。
- 已知技术栈、运行平台、目标用户和版本范围。
- 用户已提供的历史需求、会议记录、现有文档和代码资料。

## 3. 新项目流程

1. 建立项目根目录（在当前环境具备写入权限时）。
2. 创建 `docs/` 及阶段目录、代码目录；遵循 `02-directory-standards.md`。
3. 按模板职责分别复制，不得把所有模板一律放入 `docs/templates/`：
   - 正式研发文档模板（需求、设计、评审、台账等）按需复制到项目 `docs/templates/`。
   - 项目看板模板 `templates/project.md` 实例化为项目根目录 `project.md`。
   - 任务台账模板 `templates/Task_Board.md` 实例化为项目根目录 `Task_Board.md`。
   - 完成任务归档模板 `templates/done.md` 实例化为项目根目录 `plans/done.md`；若 `plans/` 不存在则创建该目录。
4. 建立项目章程、项目状态、文档清单、原始需求台账、问题台账、决策台账和变更台账。
5. 用户已有需求描述时按原文登记为 `RAW`，不要求重复输入。
6. 初始阶段设为 `P0_PROJECT_INIT`；初始化完成后状态转入 `P1_REQUIREMENT_COLLECTION`，但不代表需求确认。
7. 按 `10-project-consistency-check.md` 执行初始化后的强制只读一致性检查，并报告检查结果；不得自动修复。
8. 输出创建清单、未确认信息、风险、当前阶段和下一步。

## 4. 已有项目接管流程

1. 只读扫描目录结构、代码、README、研发文档、模板、台账、Git 状态（若可访问）和已批准基线。
2. 区分已有内容、缺失内容、重复内容、冲突内容和未知内容。
3. 识别现有技术栈与其惯用目录，不强制改造成默认结构。
4. 形成《项目现状扫描报告》，列明建议新增/补齐/迁移项及风险。
5. 等待用户明确批准迁移范围后再执行；不得擅自移动、覆盖、重命名或删除文件。
6. 采用现有编号继续维护；编号冲突先记录问题，不自动重编号。

## 5. 初始化输出

至少报告：项目名称/目标、项目类型、扫描或创建范围、实际创建/保留文件、未处理项、当前阶段、基线状态、阻塞问题和下一步。区分“建议创建”与“已成功创建”。

## 6. 禁止事项

- 不在初始化时自动生成正式 SRS、概要设计或详细设计。
- 不把助手建议标为用户确认。
- 不以初始化完成推断需求采集完成。
- 无写入权限时不得声称文件已写入。

## 7. V2.4 项目看板与任务台账初始化

新项目必须在根目录创建 `project.md`、`Task_Board.md`，并在 `plans/` 下创建 `done.md`。三者分别使用技能包 `templates/project.md`、`templates/Task_Board.md`、`templates/done.md`，不得误放入项目 `docs/templates/`；只有正式研发文档模板副本放入 `docs/templates/`。它们是管理记录例外，不改变研发文档归档于 `docs/` 的原则。已有项目先扫描看板、任务台账、计划/归档、TASK 编号、其他任务系统和 Git；存在同类文件时先做映射，不覆盖、重编号、合并、迁移或删除，等待用户批准后再补齐。初始化不凭空生成大量任务；只有明确执行目标且有可验证完成条件的工作才登记 TASK，需求仍进入 RAW 台账。
