# 05 阶段评审与基线规范

## 1. 状态定义

- `NOT_STARTED`：尚未启动。
- `IN_PROGRESS`：阶段工作进行中。
- `REVIEW_PENDING`：交付物已形成且检查完成，等待评审。
- `CHANGES_REQUIRED`：评审退回，必须修改后重提。
- `APPROVED`：用户明确批准指定交付物/范围。
- `BASELINED`：批准内容已固定版本并记录基线标识。

## 2. 评审准备

提交前核对：输入和基线版本明确；交付物完整；需求/设计追踪完整；冲突、遗漏、重复已检查；阻塞问题已解决；非阻塞风险已披露并获用户接受（如适用）；未验证内容已标记；验收标准可验证；变更记录完整；文档/台账版本一致；编号唯一。

评审包包含阶段、文档名称/版本、检查结果、覆盖率、问题与风险、未验证项、待用户决定和建议结论。无法计算的指标标记 `UNKNOWN`，不估算。

## 3. 评审与批准分离

提交评审只将状态设为 `REVIEW_PENDING`，不代表批准。用户可以通过“批准需求分析阶段”“批准概要设计”等清晰表达批准。模糊赞许、继续讨论或要求下一步不构成批准。

记录批准范围、文档版本、用户批准表达、附加条件和可靠日期。只批准部分内容时，只记录该范围批准，不把整个文档设为 `APPROVED`。

## 4. 建立基线

建立基线前确认批准记录、文档版本、关联台账和追踪矩阵一致。为基线分配稳定标识（例如 `REQ-BL-1.0`、`HLD-BL-1.0`），记录内容清单、日期和批准范围。基线建立后只通过变更流程更新，不直接覆盖。

## 5. 退回与有条件通过

退回意见应拆分为可执行问题并分配编号，状态设为 `CHANGES_REQUIRED`。修改后增加文档修订记录并重新检查。非阻塞问题只有在用户明确接受风险、责任和处理时机后才可带条件通过；存在阻塞项不得宣称阶段完成。

## 6. 审批记录模板字段

至少包括：阶段、评审文档与版本、评审状态、结论、批准动作、批准范围、批准表达、批准人（用户）、可靠日期、附加条件、关联问题和基线标识。

## 7. 问题澄清记录完整性门禁（V2.2）

阶段评审必须检查本阶段相关澄清问题是否均有独立台账记录，并核对：问题原文/背景/影响范围齐全；选项完整且每项有优缺点；每轮助手推荐及理由齐全；推荐置信度和依据缺口明确；用户历次回答与改选均保留；最终选择有明确用户确认依据；Q/RAW/ADR/阶段文档关联有效。

缺少候选选项、助手推荐、推荐理由或用户确认依据时，不得将对应问题视为已完成；若影响阶段交付或基线正确性，标记 `BLOCKED` 并停止阶段批准/基线建立。用户尚未确认的候选方案不得作为已批准内容进入基线。


## 8. 设计 Demo 评审与正式基线（V2.3）

### 8.1 评审对象分离

P3/P4 的 Demo 可作为对应设计评审的辅助交付物，但必须单独列明版本、Commit 和评审范围。P4 正式冻结时，详细设计文档与 Demo 是两个独立评审对象：分别检查、分别记录结论、分别取得用户明确批准。不得以“批准详细设计”自动推定 Demo 获批，反之亦然。

### 8.2 Demo 评审提交信息

至少包含：Demo 版本、Git Commit 哈希、关联 Tag（如有）、运行环境和启动方式、覆盖页面/流程、关联需求/设计章节、已知限制、未实现项、未决问题、与详细设计差异、质量检查结果及待用户决定事项。

### 8.3 正式 Demo 基线门禁

建立正式设计基线前必须同时满足：

1. P4 阶段入口条件满足，概要设计已获批准。
2. 详细设计文档已完成评审并获用户明确批准，版本和范围明确。
3. Demo 已完成评审并获用户明确批准，版本和范围明确。
4. 两项交付物之间的页面/交互/需求追踪关系和已知差异已核对；阻塞差异为零。
5. Git 仓库可用；完整 Demo 已提交，工作区无未提交的 Demo 相关变更；Tag 指向稳定集成分支上的完整 Commit。
6. 基线记录列出详细设计基线编号、Demo 版本、Commit 哈希、正式 Tag、评审记录、用户批准表达/范围和日期（可靠时）。

正式 Demo 基线建议使用 Annotated Tag，例如 `demo-v1.0`，并在消息中记录阶段、Demo 版本、详细设计基线、评审状态和用户批准状态。正式基线 Tag 不得随意删除、移动、覆盖或复用；后续变更走 CR 并创建新基线版本。

### 8.4 里程碑 Tag 与审批的区别

`demo-v0.x` 等探索/评审里程碑 Tag 只表示一个可恢复的版本快照，不代表用户批准或正式基线。只有满足上述正式门禁并有批准记录，才可建立 `demo-v1.0` 正式基线 Tag。Tag 本身不能代替评审记录和用户批准证据。

## 9. V2.4 任务完成与阶段门禁分离

TASK `DONE` 仅表示执行项满足验收条件且有完成证据，不代表阶段交付物完整、评审通过或用户批准。阶段状态只以 `Project_Status.md` 及评审/批准/基线证据为准。所有任务 DONE 不自动使阶段进入 `REVIEW_PENDING`、`APPROVED` 或 `BASELINED`。评审包应披露本阶段 TASK 覆盖、未完成/阻塞任务、DONE 证据和关联编号；任务清单不能替代正式交付物、V2.2 澄清完整性门禁或 V2.3 Demo 双重批准门禁。看板和 Git Tag 关联都不是审批证据。
